# 3d/5d/10d 主模型分支开发复盘（2026-03-10）

## 1. 目的

本文档复盘 `feature/model-3d-5d-10d-head` 从独立 `worktree` 开始到当前阶段的开发过程，重点回答：

- 哪些决策是对的；
- 哪些过程做得不够好；
- 哪些流程因为缺少标准化而反复对接、反复确认；
- 下一轮 `XGBoost` baseline 与后续主线工作应该如何避免重复踩坑。

本文档不是项目级路线图，也不替代主模型层开发计划；它只记录这条分支已经发生过的经验和教训。

---

## 2. 本轮开发范围

这次主模型分支主要完成了 4 件事：

1. 收口主线 `3d/5d/10d` schema；
2. 建立 `pred_3d/pred_5d/pred_10d -> alpha_score` 聚合层；
3. 固定 `LSTM baseline` 的身份、状态分级与默认报告；
4. 把 `LSTM` 主线评估从旧的统计摘要切到更接近交易行为的 `trade_like panel`。

对应的关键提交如下：

## 3. 做得好的地方

## 3.1 分支与工作区拆分是正确的

- `develop`、执行层、主模型、`1d` 研究线拆成独立 `worktree` 之后，开发节奏明显更清楚；
- 主模型分支可以在不打断执行层的前提下持续收口内部问题；
- 这套结构适合后续 `LSTM / XGBoost` 并行推进。

## 3.2 先收 schema，再做聚合，是正确顺序

- 先统一主线 `label / pred / weight key`，再做 `alpha_score` 聚合层，避免了后续继续散改脚本；
- `trend_schema.py` 的引入让主线输入边界第一次稳定下来；
- `alpha_score` 聚合层在此基础上落地，避免了三头输出直接成为三个并列最终入口。

## 3.3 文档没有一直拖到最后

- 根入口、模块边界、研究层口径都做了同步；
- 又单独补了一份主模型专项计划，避免项目级入口文档承载太多细节；
- 这一步对后续 `XGBoost` 接线非常关键。

## 3.4 后期开始用真实数据 smoke test，是关键转折

- 合成数据只能验证流程，不足以暴露口径问题；
- 切到真实数据后，才真正看见：
  - 单报告内部面板；
  - 统一比较脚本；
  - 更接近交易行为的评价方法
  三者并不是一个标准。

## 3.5 最终把新评估抽成共享模块是正确动作

- `trade_like_panel.py` 把主线评估逻辑从训练脚本里抽出来，降低了再次产生副本的风险；
- 新面板直接基于 `alpha_score` 的 `Top-N` 组合近似收益做判断，比早期的 pooled/weekly 摘要更接近主线真实用途；
- 这一步为后续 `XGBoost` 复用同一评估口径打下了基础。

## 4. 做得不好的地方

## 4.1 主标准建立得偏晚

- 很多关键定义不是在分支一开始就固定，而是在开发过程中逐渐明确；
- 这导致术语、计划、评估、提交粒度都经历了二次整理；
- 技术方向没有错，但“唯一主标准”建立得晚，协作成本被放大了。

## 4.2 术语边界一开始不够清楚

开发过程中反复出现过语义混用：

- `主模型层`
- `主线聚合层`
- `执行层`
- “推荐层”

其中“推荐层”尤其容易把模型输出收口和执行/交易动作混成一层，导致后续边界要靠对话反复纠正。

## 4.3 baseline 身份和最优参数状态定义太晚

- 一开始只有“当前默认配置”，但没有明确它是 `baseline` 还是“当前最优”；
- 直到后面才补 `baseline / candidate-best / frozen-best`；
- 这导致“当前参数是不是已经最优”被反复追问。

## 4.4 评估口径经历了多次迁移

这条分支先后出现过三种主评价思路：

1. 训练脚本里的 `weekly_logs + pooled OOS` 摘要；
2. `daily-CS` 统一比较；
3. `trade_like panel` 的 `alpha_score + Top-N` 交易近似评估。

问题不在于曾经做过探索，而在于旧口径没有及时降级或退出主入口，导致“哪个才算主标准”被反复确认。

## 4.5 提交粒度是在中途才整理清楚

- 一开始改动跨代码、文档、评估、计划多个方向；
- 直到准备提交时，才临时拆成“上游收口 / 聚合功能 / 文档同步”几组提交；
- 这说明变更单元在开始编码前没有先被清晰切开。

## 5. 哪些流程缺少标准化，导致反复对接

## 5.1 名词表没有在分支启动时固定

缺失项：

- 统一术语表；
- 每个术语的边界说明；
- 术语对应的代码责任区。

直接后果：

- “推荐层”是否属于主模型层被反复确认；
- 执行层是否现在就该接入 `alpha_score` 被反复讨论；
- `1d` 与 `3d/5d/10d` 的边界虽然最终明确，但中途仍多次校正。

## 5.2 工作计划入口没有在一开始标准化

分支开发中出现过几次选择：

- 是重写 `NEXT_STEPS.md`；
- 还是重写历史 roadmap；
- 还是单开一份 `3d/5d/10d` 专项开发计划。

最后证明“单开专项文档，再从入口文档挂链接”是正确做法，但这个结论是在讨论后才形成的，而不是一开始就固定。

## 5.3 baseline 状态定义没有标准模板

缺失项：

- 默认参数状态定义模板；
- 报告里必须写出的状态字段；
- 状态晋级规则。

直接后果：

- 默认配置与“当前最优参数”被混用；
- `LSTM baseline` 到底推进到什么程度，需要口头反复解释。

## 5.4 评估协议没有唯一 source of truth

缺失项：

- 主线唯一评估方法；
- 辅助评估方法的降级说明；
- 哪份报告可以作为基线晋级依据。

直接后果：

- 同一份实验会同时出现：
  - 单报告内部面板；
  - `compare_ic_reports.py`；
  - 后来的 `trade_like panel`
- 结果就是同一个问题要反复确认“现在到底看哪一个”。

## 5.5 文档同步流程没有固定节奏

缺失项：

- 代码改动后哪些文档必须同步；
- 是阶段性同步还是每次能力变更就同步；
- 是否允许保留历史版说明但不挂默认入口。

直接后果：

- `develop` 历史上留下了多份旧口径副本；
- 这次开发中也需要多次先确认文档是否已经跟上代码。

## 5.6 提交策略没有前置标准

缺失项：

- 何时拆成多个提交；
- 何时代码与文档必须分开提交；
- 何时需要先做“收口提交”，再做“新能力提交”。

直接后果：

- 提交粒度是在准备 commit 时才再次整理；
- 这增加了回顾 diff 和确认 message 的成本。

---

## 6. 这轮开发里最容易反复确认的问题

如果只看“哪些问题对话里反复出现最多”，大致就是这几类：

- `3d/5d/10d` 主线到底是不是当前唯一主模型线；
- `1d` 是否进入主线；
- `alpha_score` 属于主模型层还是执行层；
- 当前 `LSTM` 默认参数是不是已经可以叫“最优”；
- 统一比较应该看 pooled、daily-CS 还是 trade-like；
- 这次应该写进旧文档，还是单开一份专项文档；
- 这批改动应该一次大提交，还是拆成多个提交。

这些反复确认本质上都不是编码问题，而是标准化不足导致的协作开销。

---

## 7. 下一轮建议固定的标准动作

为了让下一轮 `XGBoost` baseline 或后续主线开发不再重复这类问题，建议把下面几条固定下来：

1. 分支启动当天先写专项计划，不再让项目级入口文档承载具体执行顺序。
2. 分支启动当天先固定名词表：
   - 主模型层
   - 主线聚合层
   - 执行层
3. baseline 报告必须默认带：
   - `model_track`
   - `config_profile`
   - `config_status`
4. 主线晋级只认一个默认评估口径，其他口径只能当诊断，不当主门禁。
5. 文档同步采用“能力落地后立即同步入口 + 分层文档”的方式，不再积累到后面一起补。
6. 只要改动同时跨越“代码 + 文档 + 评估口径”，就提前规划提交拆分，不要等到 commit 前再整理。

---

## 8. 当前结论

这条分支整体方向是对的：

- schema 收口是对的；
- 聚合层先行是对的；
- `LSTM baseline` 分级是对的；
- 最后把评估切到 `trade_like panel` 也是对的。

当前最大的教训不是“模型做错了”，而是：

**主标准建立得偏晚，导致术语、计划、评估、文档、提交粒度都经历了额外对接成本。**

下一轮如果先把标准动作固定，再推进 `XGBoost`，整体成本会明显更低。
